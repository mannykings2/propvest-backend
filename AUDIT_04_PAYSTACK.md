# Audit Report 04: Paystack Integration

**Date:** 2026-10-06  
**Phase:** 1 - Audit & Analysis  
**Step:** 1.4 - Paystack Integration Audit

---

## Executive Summary

Paystack integration is **functional with good reference handling** but lacks explicit idempotency guarantees:

✅ **Stable references** - Uses PropVest-generated references  
✅ **Transfer verification** - Can check status after initiation  
⚠️ **Implicit idempotency** - Relies on Paystack's reference deduplication  
⚠️ **No explicit idempotency** - No documented guarantee from Paystack  
❌ **No retry protection** - Could theoretically call twice with same reference  

---

## Transfer Initiation Flow

### Current Implementation

```go
func (p *PaystackProvider) InitiateTransfer(ctx context.Context, req *TransferRequest) (*TransferResult, error) {
    // 1. Create transfer recipient (one-time)
    recipientResponse := createRecipient(req.AccountNumber, req.BankCode, req.AccountName)
    
    // 2. Initiate transfer
    transferPayload := map[string]any{
        "source":    "balance",
        "reason":    req.Reason,
        "amount":    req.Amount,
        "recipient": recipientResponse.Data.RecipientCode,
        "reference": req.Reference,  // ← PropVest reference (e.g., "WD-ABC123")
    }
    
    transferResponse := post("/transfer", transferPayload)
    
    // 3. Return result
    return &TransferResult{
        Status:       transferResponse.Data.Status,  // pending|success|failed
        TransferCode: transferResponse.Data.TransferCode,  // Paystack's ID
        Reference:    transferResponse.Data.Reference,  // Our reference echoed back
    }
}
```

## Reference Handling

### PropVest Reference

- **Generated by:** PropVest API  
- **Format:** `WD-XXXXXXXXXXXX` (12 hex chars)  
- **Stored in:** `wallet_transactions.reference` (UNIQUE)  
- **Passed to:** Paystack in transfer request  
- **Purpose:** PropVest's stable identifier  

### Paystack Transfer Code

- **Generated by:** Paystack  
- **Format:** `TRF_xxxxxxxx` (Paystack format)  
- **Stored in:** `wallet_transactions.external_reference`  
- **Purpose:** Paystack's tracking ID  

**Relationship:**
```
PropVest Reference → Paystack API → Paystack Transfer Code
   (WD-ABC123)                          (TRF_xyz789)
```

## Idempotency Analysis

### Question: What happens if we call InitiateTransfer twice with the same reference?

**Paystack Behavior (based on typical payment provider patterns):**

```go
// First call
InitiateTransfer(reference="WD-ABC123", amount=50000)
// Result: transfer_code="TRF_001", status="pending"

// Second call (duplicate)
InitiateTransfer(reference="WD-ABC123", amount=50000)
// Expected: Return existing transfer (TRF_001)
// OR Error: "Duplicate reference"
```

**Current PropVest Code:**
```go
// In worker
result, err := provider.InitiateTransfer(ctx, transferReq)
if err != nil {
    return err  // ❌ What if it's "duplicate reference" error?
}
```

**Gap:** No explicit handling of duplicate reference scenarios.

---

## Possible Failure Scenarios

### Scenario 1: Duplicate Transfer Call

```
Worker A: InitiateTransfer(ref="WD-ABC123")
          → Paystack creates TRF_001
Worker A: Crashes before saving transfer_code
Message redelivered
Worker B: InitiateTransfer(ref="WD-ABC123") again
          → Paystack returns... what?
```

**Options:**
1. ✅ Paystack returns existing transfer (idempotent)
2. ❌ Paystack creates duplicate transfer (danger!)
3. ⚠️ Paystack returns error "duplicate reference"

**Current Code:** Doesn't handle any of these explicitly.

---

### Scenario 2: Transfer Succeeds but PropVest Doesn't Know

```
Paystack: Transfer completed successfully
PropVest: Transaction still status="pending"
Reason: Webhook missed, worker crashed, etc.
```

**Recovery:** ✅ Reconciliation worker handles this

```go
// Every 5 minutes
pendingTxns := db.Where("status = ? AND created_at < ?", "pending", 10-minutes-ago)
for txn := range pendingTxns {
    result := provider.VerifyTransfer(txn.ExternalReference)
    FinalizeWithdrawal(txn.ID, result.Status == "success", ...)
}
```

## Transfer Verification

```go
func (p *PaystackProvider) VerifyTransfer(ctx context.Context, transferCodeOrReference string) (*TransferResult, error) {
    var response struct {
        Status bool
        Data struct {
            Status string  // pending|success|failed|reversed
            TransferCode string
            Amount int64
            Reason string
        }
    }
    
    get("/transfer/" + transferCodeOrReference, &response)
    
    return &TransferResult{
        Status: response.Data.Status,
        TransferCode: response.Data.TransferCode,
        ...
    }
}
```

**Analysis:**
- ✅ Can verify status after initiation
- ✅ Works with transfer_code OR reference
- ✅ Returns current status
- ✅ Critical for reconciliation

## Paystack-Specific Considerations

### Transfer Statuses

| Status | Meaning | Action |
|--------|---------|--------|
| `pending` | Transfer initiated, waiting | Wait for webhook/reconciliation |
| `success` | Transfer completed | Finalize as success |
| `failed` | Transfer failed | Finalize as failed, unlock funds |
| `reversed` | Transfer reversed by Paystack | Finalize as failed, unlock funds |

### Reference Uniqueness

**Paystack Documentation:**
> "The reference must be unique. Duplicate references will be rejected."

**Implication:** ✅ Paystack DOES enforce reference uniqueness.

**But:** How does it reject? Error response or return existing transfer?

## Recommendations

### 🔴 Critical

1. **Document Paystack idempotency behavior**
   - Test: Call InitiateTransfer twice with same reference
   - Document: What error/response do we get?
   - Handle: Add explicit error handling

   ```go
   result, err := provider.InitiateTransfer(ctx, req)
   if err != nil {
       if strings.Contains(err.Error(), "duplicate") {
           // Fetch existing transfer by reference
           existing := provider.VerifyTransfer(ctx, req.Reference)
           return existing, nil
       }
       return nil, err
   }
   ```

2. **Add reference-based transfer lookup**
   ```go
   func (p *PaystackProvider) GetTransferByReference(ctx context.Context, reference string) (*TransferResult, error) {
       // Paystack supports lookup by reference
       return p.VerifyTransfer(ctx, reference)
   }
   ```

### 🟡 Important

3. **Add explicit idempotency check before InitiateTransfer**
   ```go
   // Before calling Paystack, check if transfer already exists
   if txn.ExternalReference != nil {
       // Transfer already initiated, verify current status
       result := provider.VerifyTransfer(ctx, *txn.ExternalReference)
       // Update based on result
       return result
   }
   
   // Only initiate if no external_reference exists
   result := provider.InitiateTransfer(ctx, req)
   ```

4. **Add webhook delivery tracking**
   - Log when webhooks arrive
   - Track missed webhooks
   - Alert if webhook missing after X minutes

## Reconciliation Analysis

**Current Implementation:** ✅ **GOOD**

```go
// Every 5 minutes
cutoff := time.Now().Add(-10 * time.Minute)
pendingTxns := db.Where("status = ? AND created_at < ?", "pending", cutoff)

for txn := range pendingTxns {
    if txn.ExternalReference == nil {
        continue  // Not yet initiated, skip
    }
    
    result := provider.VerifyTransfer(*txn.ExternalReference)
    
    switch result.Status {
    case "success":
        FinalizeWithdrawal(txn.ID, true, ...)
    case "failed", "reversed":
        FinalizeWithdrawal(txn.ID, false, ...)
    case "pending":
        // Still pending, check again next cycle
    }
}
```

**Analysis:**
- ✅ Recovers missed webhooks
- ✅ 10-minute grace period (webhook gets priority)
- ✅ Only processes transactions with transfer_code
- ✅ Idempotent (calls idempotent FinalizeWithdrawal)
- ✅ 5-minute interval is reasonable
- ⚠️ No limit on how long to keep checking pending

## Conclusion

Paystack integration is **well-implemented** with proper reference handling and reconciliation. The main gap is **lack of explicit idempotency documentation and handling**.

### Key Findings

✅ **Stable references** - PropVest controls references  
✅ **Reconciliation works** - Missed webhooks recovered  
✅ **Transfer verification** - Can check status anytime  
⚠️ **Implicit idempotency** - Relies on Paystack behavior  
❌ **No duplicate call handling** - What if worker retries transfer?  

### Risk Assessment

**Current Risk:** 🟡 **LOW-MEDIUM**

**Mitigation:** Reconciliation provides safety net, but explicit handling is better.
