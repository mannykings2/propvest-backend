# 1. Purpose

This document defines how users authenticate with the PropVest platform, how permissions are enforced, and how security-sensitive operations are protected.

It serves as the canonical reference for identity, access control, and session management.

---

# 2. Security Philosophy

Security is a system-wide concern. Every layer contributes to protecting user identities, financial assets, and sensitive data.

Guiding principles:

- Least Privilege
- Defense in Depth
- Fail Secure
- Zero Trust for Client Input
- Secure by Default
- Principle of Explicit Authorization

The backend is the final authority for all authentication and authorization decisions.

---

# 3. Authentication vs Authorization

Authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

Example request flow:

```text
Client
   │
   ▼
Login
   │
   ▼
JWT Issued
   │
   ▼
Authenticated Request
   │
   ▼
Authorization Check
   │
   ▼
Business Logic
```

Authentication must always occur before authorization.

# 6. JWT Strategy

JWT is used for stateless authentication.

Claims:

```json
{
  "sub": "user_uuid",
  "role": "investor",
  "iat": 1710000000,
  "exp": 1710000900
}
```

Required claims:

- sub
- role
- iat
- exp

Optional claims:

- iss
- aud
- jti

---

## Access Token

Purpose:

Authenticate API requests.

Lifetime:

15 minutes (recommended).

Storage:

- In-memory for browser clients
- Secure storage for native applications

Never store access tokens in localStorage if XSS risk cannot be adequately mitigated.

---

# 7. Refresh Token Strategy

Refresh tokens enable session continuity without requiring the user to log in repeatedly.

### Principles

- Long-lived
- Rotated on every use
- Revocable
- Stored hashed in the database

Recommended lifetime:

30 days.

Flow:

```text
Access Token Expires

↓

Client Sends Refresh Token

↓

Backend Validates

↓

Old Refresh Token Revoked

↓

New Refresh Token Created

↓

New Access Token Issued
```

Refresh token rotation prevents replay attacks.

---

# 8. Password Security

Passwords are never stored in plain text.

Recommended hashing algorithm:

- Argon2id (preferred)
- bcrypt (acceptable)

Password policy:

- Minimum 12 characters
- Uppercase letter
- Lowercase letter
- Number
- Special character

Passwords must be compared using constant-time comparison functions.

# 9. Email Verification

Registration flow:

```text
User Registers

↓

Verification Token Created

↓

Email Sent

↓

User Clicks Link

↓

Token Validated

↓

Email Marked Verified
```

Business rules:

- Verification tokens expire.
- Tokens are single-use.
- Resending invalidates previous tokens.

Unverified users may have restricted platform access.

---

# 10. Password Reset

Reset flow:

```text
Forgot Password

↓

Reset Token Generated

↓

Email Sent

↓

User Clicks Link

↓

New Password Submitted

↓

Token Validated

↓

Password Updated

↓

All Refresh Tokens Revoked
```

Security considerations:

- Tokens expire quickly.
- Tokens are single-use.
- Password reset invalidates all active sessions.

# 11. Session Management

Although JWT authentication is stateless, refresh tokens represent active sessions.

Each session stores:

- Device identifier (optional)
- Creation time
- Last activity
- Expiration
- Revocation status

Future enhancement:

Allow users to view and revoke active sessions from the account settings page.

# 12. Role-Based Access Control (RBAC)

Permissions are assigned to roles.

Example:

| Endpoint | Investor | Developer | Admin |
|----------|----------|-----------|-------|
| GET /properties | ✔ | ✔ | ✔ |
| POST /properties | ✘ | ✔ | ✔ |
| POST /investments | ✔ | ✘ | ✘ |
| GET /admin/dashboard | ✘ | ✘ | ✔ |

Authorization checks must occur in middleware and business services.

# 14. Security Threat Model

Potential threats include:

- Credential stuffing
- Brute-force attacks
- Token theft
- Replay attacks
- SQL injection
- Cross-Site Scripting (XSS)
- Cross-Site Request Forgery (CSRF)
- Broken access control
- Sensitive data exposure

Mitigations:

- Strong password policy
- Rate limiting
- Parameterized queries
- Input validation
- JWT expiration
- Refresh token rotation
- HTTPS enforcement
- Structured audit logging

---

# 15. Token Revocation

Refresh tokens may be revoked when:

- User logs out
- Password changes
- Account suspended
- Administrator revokes sessions
- Suspicious activity detected

Revoked tokens must never be accepted again.

---

# 16. Rate Limiting

Recommended defaults:

Anonymous users:

100 requests/minute

Authenticated users:

300 requests/minute

Login endpoint:

10 requests/minute

Password reset endpoint:

5 requests/hour

These values should remain configurable.

---

# 17. Audit Logging

Security-sensitive actions must be recorded.

Examples:

- Login success
- Login failure
- Password reset
- Email verification
- Role change
- Account suspension
- Refresh token revocation
- Wallet withdrawal
- Property approval

Audit logs should include:

- Timestamp
- User ID
- Action
- IP address
- User agent
- Request ID

Audit records are append-only and immutable.

```text

        │
        ▼
```

```text
        │
   No ─────► 401 Unauthorized
        │
       Yes
        │
        ▼

        │
   No ─────► 401 Unauthorized
        │
       Yes
        │
        ▼

        │
   No ─────► 401 Unauthorized
        │
       Yes
        │
        ▼

        │

        │
       Yes
```
