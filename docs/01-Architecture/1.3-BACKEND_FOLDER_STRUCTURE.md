# 1. Purpose

This document defines the **official backend folder structure** for the PropVest backend.

This document supersedes every previous folder organization proposal.

Every engineer and AI coding agent must follow this structure.

---

# 2. Architecture Philosophy

The backend follows a **Layered (Cross-Cutting)** architecture.

Instead of grouping code by feature folders, code is grouped by responsibility.

Example:

```text
handlers/

services/

repositories/

models/

middleware/
```

rather than

```text
auth/

wallet/

property/
```

This architecture was chosen because it:

- makes responsibilities explicit
- is beginner friendly
- aligns with traditional enterprise backends
- simplifies learning
- mirrors many production Go services
- works well with Clean Architecture principles

# 6. Layer Responsibilities

## Routes

Registers endpoints.

Example

```
POST /auth/login
```

↓

Auth Handler

---

## Handlers

Responsibilities

- parse requests
- call services
- return responses

Should NEVER

- query database
- hash passwords
- implement business rules

---

## Services

The heart of the application.

Responsibilities

- business logic
- transactions
- orchestration
- event publishing

Should NEVER

- parse HTTP
- return JSON

---

## Repositories

Responsibilities

- CRUD
- SQL/GORM
- pagination
- filtering

Should NEVER

- send emails
- validate JWT
- implement business rules

---

## Models

Represents database entities.

Examples

User

Wallet

Investment

Property

Transaction

---

## DTO

Represents API payloads.

Example

```
dto/

auth/

wallet/

property/

investment/

admin/

user/
```

DTOs are organized by feature because they grow rapidly.

---

## Middleware

Cross-cutting concerns.

Examples

JWT

Recovery

Logger

Rate Limiter

Request ID

---

## Validators

Custom validation.

Examples

Password

Investment Amount

Property Status

Phone Number

---

## Logger

Structured logging.

Zap.

JSON output.

Request IDs.

---

## Events

Domain events.

Example

```
InvestmentCreated

WalletFunded

UserRegistered
```

---

## Jobs

Background workers.

Examples

Email

Cleanup

Reports

Notifications

---

## Payments

Payment providers.

```

shared/
```

---

## Storage

Cloudinary

AWS S3

Local

---

## Cache

Redis

Future caching layer.

---

## Response

Standard response builders.

```

Paginated()
```

---

## Errors

```

```

---

## Constants

Shared constants.

Roles

Statuses

Limits

Regex

---

## Utils

Small generic helpers.

Avoid business logic.

```

misc/

stuff/
```

# 14. Adding a New Feature

When introducing a feature:

1. Create DTOs
2. Create Model
3. Create Repository
4. Create Service
5. Create Handler
6. Register Routes
7. Add Tests
8. Update API Documentation

# 16. Anti-Patterns

Never

- Put SQL in handlers.
- Put HTTP in services.
- Put business logic in repositories.
- Put secrets in source code.
- Return GORM models directly.
- Mix JSON responses across handlers.
- Create "helper" packages for unrelated code.

# Appendix B – Architecture Summary

The PropVest backend adopts a layered architecture with cross-cutting directories. Responsibilities are separated by layer rather than by feature. Business logic is centralized in the service layer, persistence is isolated in repositories, and HTTP concerns are confined to handlers and routes. This structure is intended to maximize maintainability, readability, testability, and educational value while remaining suitable for a production-grade Go backend.
