# 1. Executive Summary

PropVest is a full-stack property investment platform designed to connect investors with real estate development opportunities through a secure, scalable, and production-ready web application.

The platform allows investors to discover investment opportunities, fund their wallets, invest in verified properties, monitor portfolio performance, receive notifications, and manage their profiles. Developers and administrators are provided with dedicated interfaces for property management, user administration, document verification, and operational oversight.

The backend is designed using layered architecture principles to promote maintainability, testability, and scalability. The project aims to serve as both a production-grade application and an educational codebase that demonstrates modern backend engineering practices.

# 7. Architectural Principles

The backend follows a layered architecture.

Each layer has a single responsibility.

## Layers

```text
HTTP

↓

Handlers

↓

Services

↓

Repositories

↓

Database
```

Each layer communicates only with the layer immediately beneath it.

### Handler Layer

Responsible for:

- Receiving HTTP requests.
- Parsing input.
- Validating request DTOs.
- Returning HTTP responses.

Handlers must **never** contain business logic.

---

### Service Layer

Responsible for:

- Business rules.
- Validation beyond transport concerns.
- Authorization decisions.
- Transaction coordination.
- Cross-entity workflows.

Services must not know anything about HTTP.

---

### Repository Layer

Responsible for:

- Reading data.
- Writing data.
- Database queries.
- Transactions.
- Persistence abstractions.

Repositories must not contain business rules.

---

### Database Layer

Responsible for:

- Persistent storage.
- Constraints.
- Relationships.
- Indexes.
- Transactions.

# 10. Backend Bootstrap Architecture

## Purpose

The bootstrap layer is responsible for initializing the application and assembling every dependency required by the backend.

It should contain **no business logic**.

The bootstrap layer answers one question:

> "How does the application start?"

---

## Startup Sequence

The backend startup process follows the sequence below.

```text
Application Starts
        │
        ▼
Load Environment Variables
        │
        ▼
Validate Configuration
        │
        ▼
Initialize Logger
        │
        ▼
Connect PostgreSQL
        │
        ▼
Configure Connection Pool
        │
        ▼
Run Database Migrations
        │
        ▼
Create Router
        │
        ▼
Register Middleware
        │
        ▼
Register Routes
        │
        ▼
Create HTTP Server
        │
        ▼
Listen for Requests
```

Every startup stage must succeed before progressing to the next stage.

If any critical dependency fails during startup, the application must terminate immediately.

---

## Why Fail Fast?

A backend should never continue running when one of its critical dependencies has failed.

Examples include:

- Database unavailable
- Invalid JWT secret
- Invalid configuration
- Missing environment variables

Instead of accepting requests that are guaranteed to fail later, the application exits with a clear startup error.

The composition root is the location where every dependency is created.

Current implementation:

```text

↓

Configuration

↓

Database

↓

Router

↓

Handlers

↓

HTTP Server
```

Target production architecture:

```text
main.go
     │
     ▼
Bootstrap
     │
     ▼
Repositories
     │
     ▼
Services
     │
     ▼
Handlers
     │
     ▼
Router
     │
     ▼
HTTP Server
```

Only the composition root is allowed to construct dependencies.

Individual packages must never instantiate other layers directly.

For example:

✔ Good

```go
userRepo := repository.NewUserRepository(db)

userService := service.NewUserService(userRepo)

userHandler := handler.NewUserHandler(userService)
```

✘ Avoid

```go
func Register(...) {

repo := repository.NewRepository()

}
```

Creating dependencies inside handlers tightly couples the code and makes testing significantly more difficult.

# 20. Database Architecture

## Overview

The database is the system of record for PropVest. Every business operation ultimately persists or retrieves data through PostgreSQL.

The backend uses **GORM** as its Object-Relational Mapper (ORM) to interact with PostgreSQL while retaining the ability to execute raw SQL for performance-critical operations.

### Database Goals

- Data integrity
- ACID-compliant transactions
- High availability
- Referential integrity
- Efficient querying
- Predictable migrations
- Horizontal application scaling

---

## Database Technology Stack

| Component | Technology |
|------------|------------|
| Database | PostgreSQL |
| ORM | GORM |
| Driver | pgx / postgres |
| UUID Generation | google/uuid |
| Migration (Current) | AutoMigrate |
| Migration (Target) | golang-migrate |

---

## Database Design Principles

The schema follows these principles:

- Normalize until performance requires denormalization.
- Every table has a primary key.
- Foreign keys enforce relationships.
- Use UUIDs instead of auto-incrementing IDs.
- Timestamp every business entity.
- Soft-delete only where business requirements justify it.
- Prefer constraints over application-only validation.

---

```text
Create Investment

↓

Create Transaction Record

↓

Update Property Funding

↓

Commit
```

If **any** operation fails:


Use transactions whenever:

- Multiple tables are modified.
- Financial data changes.
- Wallet balances change.
- Investment state changes.
- Payment webhooks are processed.

Avoid transactions for simple read-only queries.

# 32. Security Architecture

## Overview

Security is a foundational concern rather than a feature. Every layer of the application contributes to protecting user data, financial transactions, and platform integrity.

Security responsibilities are distributed across:

- Infrastructure
- HTTP Layer
- Middleware
- Authentication
- Authorization
- Validation
- Database
- Storage
- Logging
- Deployment

---

## Security Objectives

The system must guarantee:

- Confidentiality
- Integrity
- Availability
- Accountability
- Non-repudiation (where applicable)

---

## Security Layers

```text
Internet
    │
HTTPS
    │
Reverse Proxy
    │
Gin Router
    │
Recovery Middleware
    │
Rate Limiter
    │
CORS
    │
Authentication
    │
Authorization
    │
Validation
    │
Business Logic
    │
Database
```

Every layer assumes the previous one may be bypassed or compromised and therefore performs its own validation.

---

## Authentication Strategy

Authentication is based on JSON Web Tokens (JWT).

### Access Token

Purpose:

Authenticate API requests.

Lifetime:

15–30 minutes.

Stored:

- Memory (preferred for web)
- Secure storage for trusted native clients

---

### Refresh Token

Purpose:

Obtain a new access token without requiring the user to log in again.

Lifetime:

7–30 days (configurable).

Refresh tokens should be:

- Rotated
- Revocable
- Stored securely
- Tracked in the database

---

## Password Storage

Passwords must never be encrypted.

Passwords must always be **hashed** using:

bcrypt

or

Argon2id.

The backend never stores or logs plain-text passwords.

---

## Authorization Model

Role-Based Access Control (RBAC) is used.

Current roles:

- Investor
- Developer
- Administrator

Future:

- Support
- Finance
- Compliance
- Super Admin

Authorization is enforced exclusively by the backend.

The frontend may hide controls for usability but cannot enforce permissions.

---

## Input Validation

Every external input is considered untrusted.

Validation occurs at:

- DTO Layer
- Service Layer (business rules)
- Database constraints

Validation includes:

- Required fields
- Length
- Format
- Enum values
- Numeric ranges
- Cross-field validation

---

## SQL Injection Prevention

Database interaction occurs through GORM.

Parameterized queries must be used whenever raw SQL is necessary.

Never concatenate user input into SQL statements.

---

## XSS Prevention

The API returns JSON only.

Frontend components must escape user-generated content before rendering.

---

## CSRF

Because authentication is based on bearer tokens rather than cookies, CSRF risk is significantly reduced.

If cookie-based authentication is introduced in the future, CSRF protection must be added.

---

## Secrets Management

Secrets include:

- JWT secret
- Database credentials
- Cloudinary keys
- SMTP credentials
- Payment provider secrets

Secrets must never be:

- Committed to Git
- Logged
- Embedded in source code

Production secrets should be managed by a secure secret management solution.

---

## Rate Limiting

Recommended limits:

Anonymous requests:

100 requests/minute

Authenticated requests:

300 requests/minute

Authentication endpoints:

10 requests/minute

These values should remain configurable.
