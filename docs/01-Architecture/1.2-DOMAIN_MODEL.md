# 1. Purpose

This document describes the **business domain** of PropVest.

Unlike `DATABASE_DESIGN.md`, which focuses on tables and relationships, this document explains:

- What each entity represents
- Why it exists
- How it behaves
- Which business rules govern it
- How it interacts with other entities

The domain model should remain stable even if the database schema or API changes.

---

# 2. What is a Domain Model?

A domain model represents the business concepts of the application.

Example:

A **Wallet** is not simply a table.

A Wallet represents:

- available investment funds
- financial ownership
- transaction history
- balance validation
- investment purchasing power

Likewise,

A Property is not just a database record.

It represents:

- a real investment opportunity
- funding progress
- ownership
- investment capacity
- expected returns

The database stores data.

The domain model explains meaning.

---

# 3. Domain Philosophy

The PropVest domain follows several principles.

## Business First

Business rules should drive software design.

Not the database.

Not the frontend.

Not the framework.

---

## Rich Domain

Every entity should represent behavior.

Not merely data.

Bad

```go
type Wallet struct {
    Balance float64
}
```

Better

```go
Wallet.CanWithdraw()

Wallet.Deposit()

Wallet.Withdraw()

Wallet.CanInvest()
```

---

## Explicit Business Rules

Rules should be expressed directly.

Example:

Instead of

```
wallet.balance -= amount
```

Prefer

```
wallet.Withdraw(amount)
```

because the domain object can enforce:

- sufficient funds
- positive amount
- transaction creation
- audit logging

# 6. User Aggregate

## Purpose

Represents an authenticated platform participant.

Roles include:

Investor

Developer

Administrator

---

## Responsibilities

Authenticate

Own Wallet

Own Investments

Receive Notifications

Upload Documents

Manage Profile

---

## Lifecycle

```
Registered

↓

Email Verification

↓

Active

↓

Suspended (optional)

↓

Archived
```

---

## Business Rules

Email must be unique.

Password must be hashed.

Role cannot be null.

One user owns exactly one wallet.

# 19. Business Invariants

The following must always be true:

- Every user owns exactly one wallet.
- Wallet balances are never negative.
- Completed transactions are immutable.
- Investments require sufficient wallet balance.
- Properties cannot exceed funding goals.
- Only approved properties accept investments.
- Deleted users cannot authenticate.
- Suspended users cannot invest.
- Every payment reference is unique.
- Every audit log entry is immutable.

Violating these invariants indicates a defect in the application.
