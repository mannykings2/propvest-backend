# 1. Purpose

This document defines the public REST API for the PropVest backend.

It serves as the contract between:

- Frontend Engineers
- Backend Engineers
- QA Engineers
- Mobile Developers
- AI Coding Agents

No API should be implemented without first being documented here.

---

# 2. API Design Philosophy

The API follows REST principles while prioritizing consistency and developer experience.

Goals:

- Predictable endpoints
- Consistent JSON responses
- Explicit validation
- Stateless communication
- Clear versioning
- Secure authentication
- Minimal breaking changes

---

# 4. Versioning

Every endpoint is prefixed with:

```
/api/v1
```

Future breaking changes should be introduced under:

```
/api/v2
```

rather than modifying existing endpoints.

---

# 5. Authentication

Protected endpoints require a Bearer JWT.

Example:

```
Authorization: Bearer <access_token>
```

Public endpoints do not require authentication.

---

# 6. Authorization

Supported roles:

- Investor
- Developer
- Administrator

Role enforcement is handled by backend middleware and services.

---

# 7. Request Standards

Content-Type:

```
application/json
```

For uploads:

```
multipart/form-data
```

Request bodies must:

- be valid JSON
- pass DTO validation
- reject unknown fields where appropriate

# 15. Authentication APIs

## POST /auth/register

Purpose

Create a new account.

Authentication

Not Required

Request

```json
{
  "first_name": "John",
  "last_name": "Doe",
  "email": "john@example.com",
  "password": "SecurePassword123!",
  "role": "investor"
}
```

Validation

- email unique
- password strength
- role valid
- required fields present

Response

HTTP 201

```json
{
  "success": true,
  "message": "User registered successfully.",
  "data": {
    "id": "uuid",
    "email": "john@example.com"
  }
}
```

Possible Errors

400

409

422

500

---

## POST /auth/login

Purpose

Authenticate a user.

Request

```json
{
  "email": "john@example.com",
  "password": "SecurePassword123!"
}
```

Response

```json
{
  "success": true,
  "data": {
    "access_token": "...",
    "refresh_token": "...",
    "expires_in": 900,
    "user": {}
  }
}
```

Errors

401

422

429

---

## POST /auth/logout

Purpose

Invalidate the current refresh token.

Authentication

Required

Response

HTTP 204

---

## POST /auth/refresh

Purpose

Issue a new access token.

Authentication

Refresh Token Required

Request

```json
{
  "refresh_token": "..."
}
```

Response

```json
{
  "success": true,
  "data": {
    "access_token": "...",
    "expires_in": 900
  }
}
```

# 16. User APIs

## GET /users/me

Purpose

Return the authenticated user's profile.

Authentication

Required

Response

```json
{
  "success": true,
  "data": {
    "id": "uuid",
    "first_name": "John",
    "last_name": "Doe",
    "email": "john@example.com",
    "role": "investor",
    "avatar_url": null
  }
}
```

---

## PATCH /users/me

Purpose

Update the authenticated user's profile.

Allowed Fields

- first_name
- last_name
- phone
- avatar_url

Validation

- phone format
- maximum lengths
- immutable email unless using dedicated verification flow

---

## PATCH /users/avatar

Content-Type

multipart/form-data

Purpose

Upload or replace profile picture.

Validation

- JPEG/PNG/WebP only
- maximum file size
- ownership enforced

Response

Returns updated avatar URL.

# 17. Wallet APIs

The Wallet module manages user balances, funding, withdrawals, and transaction history.

---

## GET /wallet

### Purpose

Retrieve the authenticated user's wallet.

### Authentication

Required

### Roles

- Investor
- Developer
- Administrator

### Response

```json
{
  "success": true,
  "data": {
    "id": "wallet_uuid",
    "balance": 250000.00,
    "currency": "NGN",
    "created_at": "2026-08-15T10:00:00Z",
    "updated_at": "2026-08-15T10:00:00Z"
  }
}
```

---

## POST /wallet/deposit

### Purpose

Initialize wallet funding.

### Authentication

Required

### Request

```json
{
    "amount": 50000
}
```

### Validation

- amount > 0
- minimum deposit amount
- maximum deposit amount

### Flow

```
Client

↓

Backend

↓

Payment Provider

↓

Authorization URL

↓

User Pays

↓

Webhook

↓

Wallet Updated
```

### Response

```json
{
    "success": true,
    "data": {
        "authorization_url": "...",
        "reference": "PAY-XXXXXX"
    }
}
```

---

## POST /wallet/withdraw

### Purpose

Withdraw wallet funds.

### Authentication

Required

### Request

```json
{
    "amount": 10000,
    "bank_account_id": "uuid"
}
```

### Business Rules

- sufficient balance
- account verified
- withdrawal limits
- KYC completed

---

## GET /wallet/transactions

### Purpose

Retrieve wallet history.

### Query Parameters

```
?page=1

?limit=20

?type=deposit

?status=completed

?sort=created_at
```

### Response

Paginated transaction list.

# 24. Idempotency

Endpoints that create financial records must support idempotency.

Examples

Wallet funding

Investments

Withdrawals

Webhook processing

Client sends

```
Idempotency-Key
```

Header.

Duplicate requests with the same key must return the original response rather than creating duplicate records.

---

# 25. Webhook Specification

External providers communicate through secure webhooks.

Supported Providers

- Paystack
- Flutterwave (future)

Processing Pipeline

```
Receive Request

↓

Verify Signature

↓

Validate Payload

↓

Check Idempotency

↓

Database Transaction

↓

Update Records

↓

Respond 200
```

Never trust webhook payloads without signature verification.

# 27. API Security Guidelines

- All protected endpoints require JWT authentication.
- Sensitive operations require authorization checks.
- Input validation is mandatory.
- File uploads require MIME type validation.
- Request payload size limits must be enforced.
- Rate limiting protects against abuse.
- Audit logs record security-sensitive operations.
