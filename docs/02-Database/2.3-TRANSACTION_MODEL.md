# 1. Purpose

The Transaction Model is the financial backbone of PropVest.

Every movement of money must produce an immutable transaction record.

Transactions provide:

- Financial history
- Auditability
- Traceability
- Reconciliation
- Regulatory support
- User account statements

No financial operation should occur without creating one or more transaction records.

---

# 2. What is a Transaction?

A transaction represents a financial event.

Examples:

- Wallet deposit
- Investment purchase
- Withdrawal
- Refund
- Profit distribution
- Administrative adjustment
- Fee deduction

A transaction is **not** the wallet balance.

The wallet balance changes **because** transactions occur.

---

# 3. Transaction Philosophy

The system follows these principles:

- Transactions are immutable.
- Transactions are append-only.
- Transactions are auditable.
- Transactions are timestamped.
- Transactions never disappear.
- Corrections are made with compensating transactions—not edits.

Never update or delete historical financial records.

---

# 4. Financial Integrity Principles

Every transaction must satisfy:

- Exactly one origin
- Exactly one business purpose
- Complete audit trail
- Deterministic calculations
- Atomic execution
- Consistent state

Financial correctness always takes priority over performance.

# 5. Transaction Lifecycle

```text
Business Action

↓

Validation

↓

Begin Database Transaction

↓

Create Ledger Entries

↓

Update Wallet Balance

↓

Commit Database Transaction

↓

Publish Event

↓

Notify User
```

If any step fails before commit:

- Roll back the database transaction.
- Do not partially update balances.

# 10. Double-Entry Ledger

PropVest should adopt a **double-entry accounting model** as the platform matures.

Example:

User deposits ₦100,000.

Ledger:

```text
Debit

Payment Clearing Account

₦100,000

Credit

User Wallet

₦100,000
```

Another example:

Investment

```text
Debit

Investor Wallet

₦50,000

Credit

Investment Escrow

₦50,000
```

Benefits:

- No money is created accidentally.
- Easier reconciliation.
- Easier auditing.
- Industry-standard accounting.

# 14. Idempotency

Every financial request should include an **idempotency key**.

Example:

```text
X-Idempotency-Key:
9b1deb4d-3b7d-4bad-9bdd-9f5d6f6d2b15
```

If the same request is received twice:

- Return the original response.
- Do not create duplicate transactions.
- Do not credit the wallet twice.

Idempotency is mandatory for payment-related endpoints.

---

# 15. Atomicity

Financial operations must execute within a single database transaction.

Example:

```text
Begin

↓

Create Transaction

↓

Update Wallet

↓

Create Investment

↓

Commit
```

If any step fails:

```text
Rollback
```

Partial updates are unacceptable.

---

# 16. Concurrency

Concurrent requests may attempt to modify the same wallet.

Strategies:

- Row-level locking
- Database transactions
- Optimistic locking (future)
- Serializable operations for critical financial updates

Prevent race conditions that could produce incorrect balances.

---

# 17. Reconciliation

Daily reconciliation should compare:

- Internal transaction records
- Wallet balances
- Payment provider records
- Bank settlement reports (future)

Differences must generate alerts for investigation.

---

# 18. Auditing

Every transaction should record:

- User
- Timestamp
- Source
- IP address (where appropriate)
- Device (optional)
- Reference
- Related business entity

Audit logs must be immutable.

# 22. Performance Considerations

- Index frequently queried columns.
- Paginate transaction history.
- Archive historical records when appropriate.
- Batch reconciliation jobs.
- Avoid N+1 query patterns.
- Optimize date-range queries.

Transaction history is expected to become one of the largest tables in the system.

# 24. Anti-Patterns

Never:

- Delete financial transactions.
- Edit completed transactions.
- Store balances without transaction history.
- Credit wallets before payment verification.
- Ignore idempotency.
- Perform financial updates outside database transactions.
- Use floating-point data types for money.

Always store monetary values using fixed-precision decimal types (or integer minor units where appropriate) to avoid rounding errors.
