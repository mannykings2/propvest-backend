# 1. Purpose

The database is the authoritative source of truth for the PropVest platform.

Every business operation ultimately persists data to PostgreSQL.

This document defines:

- every entity
- every relationship
- every constraint
- every index
- every transaction
- future schema evolution

No schema changes should be introduced without updating this document.

---

# 2. Database Philosophy

The schema follows four principles:

## Accuracy

Represent business concepts correctly.

## Integrity

Use constraints to prevent invalid data.

## Performance

Design for efficient reads and writes.

## Maintainability

Schemas should evolve through versioned migrations rather than manual database changes.

# 4. Design Principles

Every table should:

- have a UUID primary key
- contain created_at
- contain updated_at
- contain deleted_at only when soft deletion is required
- define foreign keys explicitly
- use indexes for frequently queried fields
- avoid nullable columns unless business rules require them

---

# 5. Naming Conventions

## Tables

Plural, snake_case.

Examples:

users

wallets

properties

investments

transactions

---

## Columns

snake_case.

Examples:

created_at

wallet_balance

developer_id

property_id

investment_amount

---

## Foreign Keys

Always:

```
user_id

wallet_id

property_id
```

Never:

```
uid

userid

walletID
```

---

# 6. UUID Strategy

Every entity uses UUID as its primary key.

Example:

```
id UUID PRIMARY KEY
```

Advantages:

- globally unique
- difficult to enumerate
- microservice friendly
- replication friendly

---

# 7. Timestamp Strategy

Every entity contains:

```
created_at

updated_at
```

Optional:

```
deleted_at
```

---

# 8. Soft Delete Strategy

Use soft deletes only for entities that may require restoration or auditability.

Recommended:

Users

Properties

Documents

Avoid soft delete for immutable financial records such as transactions.

Purpose:

Represents every authenticated person in the platform.

Fields:

| Column | Type | Notes |
|---------|------|------|
| id | UUID | PK |
| first_name | VARCHAR | |
| last_name | VARCHAR | |
| email | VARCHAR | Unique |
| password_hash | TEXT | |
| role | ENUM | investor/developer/admin |
| phone | VARCHAR | Nullable |
| avatar_url | TEXT | Nullable |
| email_verified | BOOLEAN | |
| status | ENUM | active/suspended/pending |
| created_at | TIMESTAMP | |
| updated_at | TIMESTAMP | |

- email UNIQUE
- role
- status

# 23. Indexing Strategy

Primary indexes:

- email
- property status
- property location
- developer_id
- transaction reference
- created_at

Composite indexes should be introduced after observing production query patterns.

---

# 24. Transactions

Wrap these operations in database transactions:

- Register User + Wallet Creation
- Wallet Deposit
- Wallet Withdrawal
- Investment Purchase
- Payment Webhook Processing

Either all operations succeed or none do.

---

# 25. Migration Strategy

Development:

AutoMigrate

Production:

golang-migrate

Every migration should be:

- versioned
- reversible
- peer reviewed

---

# 26. Data Integrity Rules

Examples:

- One wallet per user.
- Wallet balances cannot become negative.
- Completed transactions are immutable.
- Investments cannot exceed available wallet balance.
- Properties cannot exceed funding goals.

---

# 27. Performance Considerations

- Use indexes for common queries.
- Paginate large result sets.
- Avoid SELECT * in production queries.
- Batch inserts where appropriate.
- Monitor slow queries.
- Tune connection pools.
