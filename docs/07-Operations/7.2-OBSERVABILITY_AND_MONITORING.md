# 1. Purpose

Observability enables engineers to understand the internal state of the backend by examining the data it produces.

It answers questions such as:

- Is the system healthy?
- Why is it slow?
- Which endpoint is failing?
- Which database query is expensive?
- Which deployment introduced a regression?

Observability is a core production requirement, not an optional feature.

---

# 2. Observability Philosophy

Every request should be traceable.

Every important business event should be measurable.

Every production issue should leave evidence.

The system should tell engineers what is happening before users report problems.

---

# 3. The Three Pillars of Observability

```text
            Observability

        ┌─────────┬─────────┐
        │         │         │
        ▼         ▼         ▼

     Metrics    Logs     Traces
```

Each pillar answers different questions.

| Pillar | Answers |
|---------|----------|
| Metrics | What is happening? |
| Logs | What happened? |
| Traces | Why did it happen? |

---

# 4. Metrics

Metrics are numerical measurements collected over time.

Examples:

- Requests per second
- Error rate
- Memory usage
- CPU utilization
- Database latency

Metrics should be inexpensive to collect.

---

# 5. Logging

Logs record events.

Examples:

```text
User Logged In

Investment Created

Wallet Funded

Payment Failed
```

All production logs should be structured JSON.

---

# 6. Distributed Tracing

A trace follows a request through multiple services.

Example

```text
Frontend

↓

API

↓

Wallet Service

↓

Payment Provider

↓

Webhook

↓

Database
```

Each operation becomes a span.

Every span belongs to a trace.

# 9. Error Budgets

If the API has a 99.9% availability target:

Maximum downtime per month:

≈ 43 minutes

Error budgets determine how much instability is acceptable before feature development pauses to improve reliability.

# 22. Runbooks

Every critical alert should have a documented runbook.

Example

High Database CPU

Checklist

1. Check slow queries
2. Check locks
3. Check recent deployment
4. Review dashboards
5. Scale if necessary

Runbooks reduce incident response time.

# Appendix C – Monitoring Maturity Model

### Level 1

- Basic logs
- Health endpoint

### Level 2

- Metrics
- Dashboards

### Level 3

- Distributed tracing
- Structured alerts

### Level 4

- Predictive monitoring
- Capacity planning
- Automated remediation

The goal for PropVest is to achieve **Level 3** before production launch, with a roadmap toward **Level 4** as the platform scales.
