# 1. Purpose

This document defines how the PropVest backend is deployed, monitored, secured, and operated in production.

Deployment should be:

- Repeatable
- Automated
- Secure
- Observable
- Easily recoverable

---

# 2. Deployment Philosophy

Every deployment must be:

- Automated
- Versioned
- Tested
- Reversible

No manual server modifications.

Servers are treated as replaceable infrastructure.

---

# 3. Environment Strategy

Maintain separate environments:

```text
Developer Machine

↓

Development

↓

Staging

↓

Production
```

Each environment has:

- Separate database
- Separate secrets
- Separate storage
- Separate logging

Never share production resources with development.

---

# 5. Development Environment

Runs locally using Docker Compose.

Services:

- Backend API
- PostgreSQL
- Redis
- pgAdmin
- Mailpit (SMTP testing)

Goals:

- Fast startup
- Easy debugging
- Minimal configuration

---

# 6. Staging Environment

Purpose:

Validate production changes before release.

Should mirror production:

- Same OS
- Same Docker images
- Same PostgreSQL version
- Same Redis version

Use staging API keys where applicable.

---

# 7. Production Environment

Characteristics:

- HTTPS only
- Automated backups
- Centralized logs
- Monitoring enabled
- Alerts configured
- Read-only infrastructure changes through CI/CD

---

# 8. Docker Strategy

Every service runs in its own container.

Example:

```text
backend

postgres

redis

nginx
```

Principles:

- One process per container
- Multi-stage Docker builds
- Small final images
- Non-root user
- Read-only filesystem where practical

---

# 9. Docker Compose

Development Compose:

```text
backend

postgres

redis

pgadmin

mailpit
```

Production Compose (if used):

```text
backend

postgres

redis

nginx

watchtower (optional)
```

Avoid exposing internal services directly to the internet.

---

# 10. Reverse Proxy (Nginx)

Responsibilities:

- HTTPS termination
- Static asset delivery
- Reverse proxy
- Compression
- Security headers
- Rate limiting

Nginx should be the only public-facing HTTP server.

---

# 11. HTTPS & TLS

Use TLS for all traffic.

Recommended:

- Let's Encrypt
- Automatic renewal
- HTTP → HTTPS redirect
- HSTS enabled

Never allow plaintext HTTP in production.

---

# 12. Domain Management

Example:

```text
api.propvest.com

admin.propvest.com

docs.propvest.com
```

Separate domains improve flexibility and security.

---

# 13. Environment Variables

Never hardcode configuration.

Example:

```text
APP_ENV

APP_PORT

JWT_SECRET

JWT_REFRESH_SECRET

DATABASE_URL

REDIS_URL

CLOUDINARY_API_KEY

PAYSTACK_SECRET

SMTP_HOST
```

Provide:

```
.env.example
```

without secrets.

---

# 14. Secret Management

Secrets should come from:

- GitHub Secrets
- Cloud Secret Manager
- Docker Secrets
- Vault (future)

Never commit:

- API keys
- Passwords
- JWT secrets
- Database credentials

# 17. Database Deployment

Production database changes should occur via versioned migrations only.

Never modify schema manually.

Migration process:

```text
Backup

↓

Run Migration

↓

Verify

↓

Deploy Application
```

---

# 18. Database Migrations

Requirements:

- Idempotent
- Versioned
- Reviewed
- Reversible where practical

Every migration must have a corresponding rollback strategy.

---

# 19. Backup Strategy

Daily:

- PostgreSQL dump

Hourly:

- WAL archiving (if enabled)

Storage:

- Encrypted
- Off-site
- Versioned

Retention example:

- Daily: 30 days
- Weekly: 12 weeks
- Monthly: 12 months

---

# 20. Restore Strategy

Regularly test restoration.

Process:

```text
Provision Database

↓

Restore Backup

↓

Run Verification

↓

Reconnect Application
```

A backup that cannot be restored is not a backup.

# 24. Readiness & Liveness Probes

Liveness:

"Is the application running?"

Readiness:

"Can the application serve traffic?"

These probes are essential for container orchestration platforms such as Kubernetes.

---

# 25. Scaling Strategy

Horizontal scaling preferred.

```text
          Load Balancer
          /     |     \
         /      |      \
    API-1   API-2   API-3
         \      |      /
          PostgreSQL
```

Application instances should remain stateless.

---

# 26. Rate Limiting

Protect endpoints from abuse.

Suggested limits:

- Authentication endpoints
- Password reset
- Email verification
- Payment initialization

Implement IP-based and user-based limits.

---

# 27. Caching

Use Redis for:

- Session metadata
- Rate limiting
- Frequently accessed data
- Temporary tokens

Do not cache sensitive personal information without careful consideration.

---

# 28. Security Hardening

Enable:

- HTTPS
- HSTS
- Security headers
- Content Security Policy (where applicable)
- Input validation
- Output encoding
- Dependency scanning
- Image scanning
- Least privilege access

Regularly update dependencies.

---

# 29. Disaster Recovery

Prepare for:

- Database failure
- Server failure
- Region outage
- Secret compromise
- Accidental deletion

Maintain documented recovery procedures and recovery time objectives (RTO) / recovery point objectives (RPO).

---

# 30. Release Strategy

Preferred strategy:

```text
Blue/Green Deployment
```

Alternative:

```text
Rolling Deployment
```

Canary deployments may be introduced for high-risk releases.

---

# 31. Rollback Strategy

Every deployment must support rollback.

Steps:

1. Stop rollout.
2. Restore previous container image.
3. Restore database if migration is incompatible.
4. Verify application health.
5. Notify stakeholders.

Rollback procedures should be documented and rehearsed.

---

# 32. Deployment Checklist

Before release:

- All tests pass.
- Security scan passes.
- Migrations reviewed.
- Backups completed.
- Monitoring active.
- Alerts configured.
- Documentation updated.
- Version tagged.
- Rollback verified.

After release:

- Verify health endpoints.
- Monitor error rates.
- Monitor latency.
- Validate critical user journeys.
- Confirm background jobs are functioning.
