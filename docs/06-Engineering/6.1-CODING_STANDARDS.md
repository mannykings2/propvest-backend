# 1. Purpose

This document defines the engineering standards for every line of code written in the PropVest backend.

Its goals are to ensure:

- Consistency
- Readability
- Maintainability
- Scalability
- Security
- Testability

Every contributor, whether human or AI, must follow these standards.

---

# 2. Engineering Philosophy

Every piece of code should prioritize:

- Simplicity over cleverness
- Explicitness over magic
- Readability over brevity
- Composition over inheritance
- Interfaces over concrete dependencies
- Small focused packages
- Predictable behavior

A future engineer should understand a file within minutes.

---

# 3. Project Structure

Recommended layout:

```
cmd/
    api/

internal/

    auth/

    config/

    database/

    handlers/

    middleware/

    repositories/

    services/

    dto/

    models/

    events/

    jobs/

    notifications/

    payments/

    logger/

    utils/

pkg/

docs/

scripts/

deployments/

tests/
```

Every package should have a single responsibility.

---

# 4. Package Organization

Packages should represent business capabilities rather than technical layers whenever practical.

Good:

```
internal/auth

internal/property

internal/investment
```

Avoid:

```
controllers

models

utils

helpers
```

becoming large dumping grounds.

---

# 5. Naming Conventions

## Packages

Lowercase.

Example

```
wallet

property

investment
```

---

## Files

snake_case.go

Examples

```
wallet_service.go

wallet_repository.go

jwt_middleware.go
```

---

## Structs

PascalCase

```
UserRepository

WalletService

PropertyHandler
```

---

## Interfaces

Do not prefix with I.

Good

```
UserRepository

WalletService
```

Avoid

```
IWalletRepository

IUserService
```

---

## Variables

camelCase

Examples

```
wallet

currentUser

transactionCount
```

Avoid abbreviations unless universally understood.

---

# 6. File Naming

Every file should communicate its responsibility.

Examples

```
auth_service.go

auth_handler.go

auth_repository.go

jwt_service.go

jwt_middleware.go
```

Avoid:

```
misc.go

temp.go

helper.go

new.go
```

---

# 7. Function Design

Every function should perform one logical task.

Good

```
CreateInvestment()

VerifyPassword()

GenerateAccessToken()
```

Avoid

```
ProcessEverything()
```

Functions should generally remain under 50–80 lines unless complexity is justified.

---

# 8. Interface Guidelines

Define interfaces at the point of use rather than prematurely.

Example:

```go
type WalletRepository interface {
    FindByUserID(ctx context.Context, id uuid.UUID) (*Wallet, error)
    Update(ctx context.Context, wallet *Wallet) error
}
```

Keep interfaces small and focused.

---

# 9. Error Handling

Always return wrapped errors.

```go
return fmt.Errorf("create wallet: %w", err)
```

Never ignore returned errors.

Bad:

```go
_ = repository.Save(user)
```

Use sentinel or typed errors for business cases such as:

- ErrUserNotFound
- ErrInsufficientFunds
- ErrPropertyClosed

---

# 10. Logging Standards

Use structured logging.

Required fields:

- request_id
- user_id (when available)
- operation
- duration
- error (if applicable)

Never log:

- passwords
- JWTs
- refresh tokens
- payment secrets

---

# 11. Validation

Validate input at the application boundary.

Validation includes:

- required fields
- string lengths
- enum values
- numeric ranges
- UUID format
- email format

Business rules belong in services, not DTOs.

---

# 12. DTO Guidelines

DTOs should represent API contracts only.

They must not contain business logic or persistence concerns.

Separate DTOs for:

- Create
- Update
- Response

Avoid reusing database models as API payloads.

---

# 13. Repository Standards

Repositories are responsible only for persistence.

Allowed responsibilities:

- CRUD operations
- Query construction
- Transactions (when coordinated by services)

Repositories must not contain business rules.

---

# 14. Service Standards

Services coordinate business logic.

Responsibilities include:

- Validation of business invariants
- Orchestration across repositories
- Event publication
- Transaction coordination

Services should not know about HTTP.

---

# 15. Handler Standards

Handlers are responsible for:

- Parsing requests
- Calling services
- Returning responses

Handlers must not:

- Access the database directly
- Contain business logic
- Construct SQL queries

---

# 16. Middleware Standards

Each middleware should have one responsibility.

Examples:

- Authentication
- Authorization
- Logging
- Recovery
- Rate limiting
- Request ID
- CORS

Middleware order should be deterministic.

---

# 17. Configuration

All configuration should come from environment variables.

Never hardcode:

- API keys
- Database credentials
- Secrets
- URLs
- Ports

Provide sane defaults only for local development.

---

# 18. Database Standards

- Use UUID primary keys.
- Prefer explicit foreign keys.
- Use transactions for multi-step operations.
- Avoid raw SQL unless necessary.
- Add indexes for frequent queries.
- Use versioned migrations in production.

---

# 19. Transactions

Wrap business operations that modify multiple aggregates.

Examples:

- User registration + wallet creation
- Wallet deposit
- Investment purchase
- Payment webhook processing

Rollback on any failure.

---

# 20. Context Usage

Pass `context.Context` through all request-scoped operations.

Example:

```go
func (s *WalletService) Deposit(ctx context.Context, ...)
```

Do not store context in structs.

---

# 21. Concurrency

When using goroutines:

- Propagate context where appropriate.
- Handle synchronization explicitly.
- Avoid shared mutable state.
- Recover from panics in background workers.

Concurrency should improve performance, not obscure logic.

---

# 22. Testing Standards

Every new feature should include:

- Unit tests
- Integration tests (where applicable)

Naming:

```
wallet_service_test.go
```

Aim for:

- Happy path
- Validation failures
- Authorization failures
- Edge cases
- Error propagation

---

# 23. Documentation Standards

Every exported type and function should have a GoDoc comment.

Public APIs must be reflected in:

- API_SPECIFICATION.md
- Swagger/OpenAPI

Architecture changes require updates to:

- SYSTEM_ARCHITECTURE.md
- DOMAIN_MODEL.md
- DATABASE_DESIGN.md

---

# 24. Git Standards

Branch naming:

```
feature/auth-refresh-tokens

feature/wallet-deposits

bugfix/payment-webhook

hotfix/login-timeout
```

Commit messages:

```
feat(auth): implement refresh token rotation

fix(wallet): prevent negative balances

refactor(property): extract repository interface
```

---

# 25. Pull Request Standards

Each PR should include:

- Summary
- Motivation
- Related issue
- Database changes
- API changes
- Screenshots (if UI)
- Test evidence
- Rollback considerations

Keep PRs focused and reasonably sized.

# 26. Code Review Checklist

Reviewers should verify:

- Correctness
- Readability
- Security
- Performance
- Error handling
- Logging
- Tests
- Documentation
- Naming consistency
- Dependency impact

---

# 27. Performance Guidelines

- Avoid N+1 queries.
- Paginate collections.
- Select only required columns.
- Reuse database connections.
- Cache read-heavy data where appropriate.
- Profile before optimizing.

---

# 28. Security Standards

- Hash passwords with Argon2id (preferred) or bcrypt.
- Validate all user input.
- Use parameterized queries.
- Enforce HTTPS in production.
- Rotate secrets regularly.
- Store refresh tokens hashed.
- Verify webhook signatures.
- Implement rate limiting.
- Record security-sensitive actions in audit logs.

---

# 29. Common Anti-Patterns

Avoid:

- Fat handlers
- Fat repositories
- God services
- Global mutable state
- Circular dependencies
- Hidden side effects
- Panic-based control flow
- Silent error handling
- Duplicated validation logic
- Utility packages that become catch-alls

---

# 30. Definition of Production-Ready Code

Code is considered production-ready when it:

- Solves the intended business problem.
- Passes automated tests.
- Is reviewed.
- Is documented.
- Uses structured logging.
- Handles errors consistently.
- Is secure by default.
- Follows project conventions.
- Is maintainable by another engineer.
- Introduces no known critical defects.

Production-ready code is not merely code that works—it is code that can be safely operated, extended, and maintained over time.

```text
      │
      ▼
Handler
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼

```

# Appendix B – Dependency Direction

```text
Handlers
    │
    ▼
Services
    │
    ▼
Repositories
    │
    ▼
Database
```

Dependencies should always point inward toward the domain and persistence layers. Lower layers should never depend on higher layers.
