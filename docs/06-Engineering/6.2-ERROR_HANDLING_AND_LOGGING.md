# 1. Purpose

Every production backend eventually fails.

Databases disconnect.

Payment providers timeout.

Users send invalid data.

Networks become unreliable.

A production system is judged less by **whether failures occur** and more by **how safely and predictably it handles them**.

This document defines how PropVest handles failures.

---

# 2. Engineering Philosophy

Every error must be:

- Predictable
- Logged
- Traceable
- Actionable
- Safe

Never expose implementation details to users.

Never lose useful debugging information.

---

# 3. Error Handling Principles

Every error should answer four questions:

1. What happened?
2. Where did it happen?
3. Why did it happen?
4. Can the client recover?

If an error cannot answer these questions, it is not useful.

# 4. Error Categories

## Validation Errors

Examples

- Missing email
- Invalid UUID
- Password too short

HTTP

```

```

---

## Authentication Errors

Examples

- Invalid password
- Expired JWT
- Invalid refresh token

HTTP

```

```

---

## Authorization Errors

Examples

- Investor attempting admin action
- Developer deleting another developer's property

HTTP

```

```

---

## Resource Errors

Examples

- Property not found
- Wallet not found
- Investment not found

HTTP

```

```

---

## Conflict Errors

Examples

- Duplicate email
- Duplicate username
- Already verified email

HTTP

```
409 Conflict
```

---

## Business Rule Errors

Examples

- Insufficient wallet balance
- Property fully funded
- Investment below minimum

HTTP

```
422 Unprocessable Entity
```

---

## Infrastructure Errors

Examples

- PostgreSQL unavailable
- Redis unavailable
- Cloudinary unavailable

HTTP

```
503 Service Unavailable
```

---

## Unexpected Errors

Examples

- Nil pointer
- Panic
- Unknown exception

HTTP

```

```

# 5. Standard Error Response

Every endpoint returns the same format.

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": {
        "email": [
            "Email is required."
        ]
    },
    "request_id": "req_01HXYZ..."
}
```

Benefits

- Predictable frontend integration
- Easier debugging
- Consistent API

# 7. Application Error Types

Create typed errors.

Examples

```
ErrUserNotFound

ErrWalletNotFound

ErrDuplicateEmail

ErrInvalidPassword

ErrUnauthorized

ErrForbidden

ErrPropertyClosed

ErrInsufficientFunds
```

Avoid comparing raw strings.

---

# 8. Error Propagation

Errors move upward.

```text
Database

↓

Repository

↓

Service

↓

Handler

↓

HTTP Response
```

Each layer may wrap the error with additional context.

Never discard the original cause.

---

# 9. Handler Responsibilities

Handlers:

- Validate requests
- Translate errors to HTTP status codes
- Return JSON responses

Handlers must NOT:

- Inspect SQL errors directly
- Panic
- Retry database operations

---

# 10. Service Responsibilities

Services:

- Apply business rules
- Return domain-specific errors
- Wrap infrastructure failures

Example

```
ErrInsufficientFunds
```

instead of

```
pq: constraint violation
```

---

# 11. Repository Responsibilities

Repositories:

- Translate database errors
- Return typed persistence errors
- Never return raw SQL messages to handlers

---

# 12. Logging Philosophy

Logs are for engineers.

Responses are for clients.

Never confuse the two.

Clients receive simple messages.

Logs contain technical detail.

---

# 13. Log Levels

## DEBUG

Development diagnostics.

Never enabled in production by default.

---

## INFO

Expected business events.

Examples

- User login
- Property created
- Investment completed

---

## WARN

Recoverable problems.

Examples

- Invalid login
- Payment retry
- Slow query

---

## ERROR

Failures requiring attention.

Examples

- Database unavailable
- Email provider failure

---

## FATAL

Application cannot continue.

Examples

- Missing environment variables
- Database initialization failure

---

# 14. Structured Logging

Never log plain text only.

Bad

```
User logged in.
```

Good

```json
{
    "level":"INFO",
    "event":"user_login",
    "user_id":"uuid",
    "request_id":"req_...",
    "ip":"203.x.x.x",
    "duration_ms":42
}
```

---

# 15. Required Log Fields

Every request log should include:

- timestamp
- request_id
- method
- path
- status
- duration_ms
- user_id (if authenticated)
- ip_address
- user_agent

---

# 16. Request ID

Every incoming request receives a unique Request ID.

Example

```
X-Request-ID

req_01J0ZABCD123
```

This ID appears in:

- Logs
- Error responses
- Monitoring systems

---

# 17. Correlation ID

If a request triggers background jobs or external services, preserve a Correlation ID.

Example flow

```text
Frontend

↓

Backend

↓

Queue

↓

Worker

↓

Email Provider
```

Every component logs the same Correlation ID for end-to-end tracing.

---

# 18. Security Logging

Log security events such as:

- Failed logins
- Password resets
- Email verification
- JWT refresh
- Role changes
- Permission denials

Never log:

- Passwords
- JWTs
- Refresh tokens
- API secrets
- Payment card data

---

# 19. Audit Logging

Audit logs capture sensitive business actions.

Examples

- Admin approved property
- Admin suspended account
- Wallet manually adjusted
- Investment cancelled

Audit logs should be immutable.

---

# 20. Performance Logging

Log slow operations.

Suggested threshold

```
> 500 ms
```

Capture:

- endpoint
- SQL duration
- external API duration
- total request time

---

# 21. External Service Logging

Every external call should log:

- provider
- endpoint
- duration
- status
- retry count

Examples

- Paystack
- Cloudinary
- SMTP
- Redis

---

# 22. Panic Recovery

Never allow a panic to crash the HTTP server.

Recovery middleware should:

1. Recover panic
2. Log stack trace
3. Return HTTP 500
4. Continue serving other requests

---

# 23. Retry Strategy

Only retry transient failures.

Safe examples

- Email delivery
- Webhook notification
- External API timeout

Do NOT automatically retry:

- Wallet deductions
- Investment creation
- Payment confirmation

These require idempotency.

---

# 24. Alerting

Trigger alerts for:

- Database offline
- Payment failures
- Authentication spikes
- High error rate
- Panic frequency
- Queue backlog

Alerts should integrate with:

- Prometheus
- Grafana
- PagerDuty (future)

---

# 25. Production Guidelines

Production logging must:

- Use JSON format
- Include Request IDs
- Rotate log files
- Support centralized aggregation
- Avoid sensitive data
- Support distributed tracing

# 27. Anti-Patterns

Never:

- Ignore returned errors.
- Log passwords or tokens.
- Return SQL errors directly.
- Swallow panics.
- Use inconsistent response formats.
- Retry non-idempotent financial operations.
- Mix audit logs with application logs.

A well-designed error handling and logging strategy makes production systems observable, debuggable, and safe to operate under failure conditions.
