# 1. Purpose

Testing ensures that new features do not break existing functionality and that the backend behaves predictably under expected and unexpected conditions.

Testing is not optional.

Every production feature must include automated tests.

---

# 2. Testing Philosophy

The PropVest backend follows these principles:

- Test behavior, not implementation.
- Write deterministic tests.
- Keep tests isolated.
- Avoid shared mutable state.
- Every bug should result in a regression test.
- Prefer fast tests over slow tests.
- Mock only external dependencies.

---

# 3. Testing Pyramid

```text
               ▲
             E2E Tests
          (Few, Expensive)

       Integration Tests
     (Moderate Number)

      Unit Tests
(Many, Fast, Isolated)
               ▼
```

Approximate distribution:

- 70% Unit Tests
- 20% Integration Tests
- 10% End-to-End Tests

---

# 4. Types of Tests

| Test Type | Purpose |
|------------|---------|
| Unit | Test individual functions and business logic |
| Integration | Test interactions between layers |
| End-to-End | Test complete user workflows |
| Load | Validate performance under traffic |
| Security | Validate security assumptions |
| Regression | Prevent previously fixed bugs from returning |

# 6. Unit Testing

Unit tests verify a single unit of behavior.

Example:

```
WalletService.Deposit()
```

Should verify:

- positive amount
- zero amount
- negative amount
- repository failure
- validation failure

Unit tests should not require:

- PostgreSQL
- Redis
- Cloudinary
- Internet access

---

# 7. Integration Testing

Integration tests verify collaboration between multiple components.

Example:

```
Wallet Service

↓

Wallet Repository

↓

PostgreSQL
```

Integration tests use a real test database.

They should validate:

- SQL queries
- transactions
- constraints
- migrations

---

# 8. End-to-End Testing

E2E tests validate complete application workflows.

Example:

```text
Register

↓

Verify Email

↓

Login

↓

Fund Wallet

↓

Create Investment

↓

View Portfolio
```

These tests simulate real client behavior.

---

# 9. Repository Testing

Repository tests validate:

- CRUD operations
- filtering
- sorting
- pagination
- joins
- transactions
- indexes (where relevant)

Repositories should be tested against a real PostgreSQL instance.

---

# 10. Service Testing

Service tests verify business rules.

Example:

Investment Service

Test cases:

- wallet balance sufficient
- wallet balance insufficient
- property sold out
- duplicate investment
- transaction rollback
- event published

---

# 11. Handler Testing

Handlers should be tested using HTTP requests.

Verify:

- status code
- response body
- validation
- authentication
- authorization

Handlers should not connect directly to production databases.

---

# 12. Middleware Testing

Every middleware requires dedicated tests.

Examples:

JWT Middleware

- valid token
- expired token
- malformed token
- missing token

Rate Limiter

- within limit
- exceeding limit

Recovery Middleware

- panic recovery
- stack trace logging

---

# 13. DTO Validation Testing

Validate:

- required fields
- UUID format
- email format
- password length
- numeric limits
- enum values

Every DTO should reject invalid payloads.

---

# 14. Authentication Testing

Scenarios:

Registration

- success
- duplicate email

Login

- success
- invalid password
- locked account
- unverified email

Refresh Token

- valid
- expired
- revoked
- malformed

Logout

- token revoked
- repeated logout

---

# 15. Authorization Testing

Verify RBAC rules.

Examples

Investor

Allowed:

- invest
- wallet
- profile

Forbidden:

- approve property
- suspend users

Developer

Allowed:

- manage own properties

Forbidden:

- admin dashboard

Administrator

Allowed:

- all privileged operations

---

# 16. Database Testing

Validate:

- migrations
- constraints
- indexes
- foreign keys
- cascade behavior
- transactions
- rollback behavior

Never skip migration testing.

---

# 17. External Service Testing

External providers must be mocked.

Examples:

- Paystack
- Cloudinary
- SMTP
- Redis
- Notification provider

Never depend on third-party uptime in automated tests.

---

# 18. Mocking Strategy

Mock:

- payment gateways
- email services
- file storage
- notification providers
- queues

Do not mock:

- your business logic
- validation rules

Repository mocking is appropriate for service unit tests.

---

# 19. Test Fixtures

Store reusable data.

Examples:

```
fixtures/

user.json

wallet.json

property.json

investment.json
```

Fixtures improve consistency.

---

# 20. Test Data

Use deterministic data.

Avoid:

```
time.Now()
```

Prefer fixed timestamps.

Avoid random UUIDs unless required.

Repeatable tests produce repeatable results.

---

# 21. Performance Testing

Validate:

- response times
- concurrent requests
- database throughput
- memory usage

Suggested tools:

- k6
- Vegeta

Performance tests should run separately from unit tests.

---

# 22. Security Testing

Test:

- SQL injection
- JWT tampering
- IDOR vulnerabilities
- privilege escalation
- rate limiting
- CSRF (if applicable)
- XSS (API responses)

Verify that sensitive endpoints reject unauthorized access.

---

# 23. Regression Testing

Whenever a production bug is fixed:

1. Write a failing test.
2. Fix the bug.
3. Ensure the test passes.
4. Keep the test permanently.

Regression tests prevent bug reintroduction.

---

# 24. Continuous Integration

Every pull request should automatically run:

```text
Lint

↓

Unit Tests

↓

Integration Tests

↓

Security Scan

↓

Coverage Report

↓

Build

↓

Merge (if successful)
```

No failing test should be merged.

---

# 25. Coverage Targets

Minimum acceptable coverage:

| Layer | Target |
|---------|--------|
| Services | 90% |
| Repositories | 85% |
| Handlers | 80% |
| Middleware | 80% |
| Validators | 95% |
| Overall | 85% |

Coverage is a metric—not the goal.

Meaningful tests matter more than percentage alone.

# 26. Naming Conventions

Examples:

```
wallet_service_test.go

auth_handler_test.go

investment_repository_test.go
```

Test names:

```
TestDeposit_Success

TestDeposit_InsufficientFunds

TestLogin_InvalidPassword

TestCreateInvestment_PropertyClosed
```

Names should clearly describe the scenario.

---

# 27. Definition of Done

A feature is complete only when:

- Unit tests pass.
- Integration tests pass.
- Existing tests remain green.
- Coverage targets are maintained.
- Edge cases are tested.
- Documentation is updated.

---

# 28. Anti-Patterns

Avoid:

- Tests depending on execution order.
- Sleeping to wait for events.
- Random test data.
- Shared databases between parallel tests.
- Ignoring failing tests.
- Mocking everything.
- Testing private implementation details.

Good tests provide confidence, document expected behavior, and enable safe refactoring.
